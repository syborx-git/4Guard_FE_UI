# ADR-001: Arquitectura Nx Monorepo para 4GUARD WMS Frontend

**Estado:** Aceptado  
**Fecha:** 2026-07  
**Autores:** Equipo 4Guard Frontend

---

## Contexto

El sistema 4GUARD WMS requiere dos aplicaciones frontend con características distintas:
1. **Admin Console:** Aplicación web de escritorio para gestión y supervisión
2. **RF Terminal:** PWA para terminales de radio frecuencia y tablets de piso

Ambas aplicaciones comparten modelos de dominio, tipos TypeScript, y algunos servicios base.

## Decisión

Se adopta **Nx Monorepo** como estructura de proyecto. Ambas apps residen en el mismo repositorio bajo `apps/`, y el código compartido se extrae a `libs/shared-core`.

## Consecuencias

**Positivas:**
- Una sola instalación de `node_modules`
- Cambios en modelos compartidos propagados inmediatamente
- CI/CD más simple (un solo repositorio)
- Consistencia de versiones de Angular

**Negativas:**
- Builds más lentos (mitigado por Nx incremental builds)
- Complejidad inicial de configuración

# ADR-002: Angular Standalone Components (sin NgModules)

**Estado:** Aceptado  
**Fecha:** 2026-07

## Contexto

Angular 14+ introduce Standalone Components que elimina la necesidad de NgModules.

## Decisión

Todo nuevo componente se crea como **standalone** (`standalone: true`). Los NgModules legacy quedan deprecados en este proyecto.

## Consecuencias

- Lazy loading más granular (por componente, no solo por módulo)
- Imports más explícitos y trazables
- Compatible con Signal API de Angular 17

# ADR-003: Synexia Theme Engine (Dark/Light Mode)

**Estado:** Aceptado  
**Fecha:** 2026-07

## Contexto

El sistema necesita soporte dual de temas. Se evaluaron:
1. Angular Material theming
2. Tailwind dark: class
3. CSS Custom Properties propias

## Decisión

Se implementa el **Synexia Theme Engine** basado en CSS Custom Properties con dos clases aplicadas al `<body>`:
- `.theme-light` (por defecto en `:root`)
- `.theme-dark`

Componentes individuales se adaptan con `:host-context(.theme-dark)`.

## Consecuencias

- Transición suave entre temas (`transition: 280ms ease` en todos los elementos)
- Sin dependencia de frameworks externos
- Control total sobre los tokens de diseño

# ADR-004: RBAC Guard basado en módulos

**Estado:** Aceptado  
**Fecha:** 2026-07

## Contexto

El sistema tiene múltiples roles con distintos permisos por módulo. Se necesita controlar el acceso a rutas.

## Decisión

El `rbacGuard` verifica `data.module` de la ruta contra los permisos del usuario en el JWT. La verificación ocurre en el router, no en el componente.

```typescript
{
  path: 'carriers',
  canActivate: [rbacGuard],
  data: { module: 'carriers' },
}
```

## Consecuencias

- Permisos centralizados en el router
- Componentes limpios sin lógica de autorización
- Fácil de auditar qué rutas requieren qué permisos

# ADR-005: Estilos per-componente (no BEM global)

**Estado:** Aceptado  
**Fecha:** 2026-07

## Contexto

Se analizó usar un sistema global de clases BEM vs estilos encapsulados por componente con variables CSS locales.

## Decisión

Cada feature-level component tiene su propio archivo `.css` con variables locales en `:host`. El sistema global (`styles/`) solo contiene abstracts (variables, mixins) y componentes UI primitivos (button, card, table).

## Consecuencias

- Encapsulamiento real (Angular `ViewEncapsulation.Emulated`)
- Variables locales permiten personalización sin romper el sistema global
- Dark mode: `:host-context(.theme-dark)` por componente
- Trade-off: más CSS en bundle, pero mejor mantenibilidad
